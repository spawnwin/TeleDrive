# Бэкенд FUTBOL X

Аккаунты менеджеров, облачные сохранения и общая таблица лидеров.
Внешних зависимостей нет — только стандартная библиотека Node.js.

Данные лежат в **SQLite** (встроенный модуль `node:sqlite`, нужен Node 22+).
На более старом Node сервер запустится и сам откатится на JSON-файл, о чём
напишет в лог, — но для нормальной работы ставьте Node 22.

## Запуск

```bash
cd football-simulator/server
node server.js
```

Сервер поднимется на `http://0.0.0.0:8787` и заодно будет раздавать саму игру,
поэтому достаточно открыть `http://<адрес-компьютера>:8787` с телефона.

Переменные окружения:

| Переменная     | По умолчанию            | Назначение                              |
|----------------|-------------------------|-----------------------------------------|
| `PORT`         | `8787`                  | порт                                    |
| `HOST`         | `0.0.0.0`               | интерфейс                               |
| `DB_FILE`      | `server/data/futbolx.json` | путь к базе; для SQLite расширение меняется на `.sqlite` |
| `ALLOW_ORIGIN` | `*`                     | значение `Access-Control-Allow-Origin`  |

## Тесты

```bash
node test.js
```

Поднимает сервер на свободном порту и проходит по API настоящими HTTP-запросами:
регистрация, вход, выход, запись и чтение сохранения, удаление аккаунта,
хеширование пароля, ограничение перебора, защита от обхода каталога и лимит
размера тела запроса. Отдельный блок проверяет базу: уникальность имени на
уровне СУБД, каскадное удаление сессий и сохранения, режим WAL, сортировку
таблицы лидеров и однократность переноса из JSON.

## База данных

Схема создаётся при первом запуске:

| Таблица    | Назначение |
|------------|-----------|
| `users`    | аккаунты; `name_key` с ограничением UNIQUE — имена не задваиваются |
| `sessions` | токены сессий (только SHA-256), внешний ключ на `users` с каскадным удалением |
| `saves`    | сохранение в поле `payload`, плюс продублированные `trophies`, `division`, `wins`, `goals` |
| `meta`     | версия схемы |

Включён журнал WAL: чтение не блокирует запись, а обрыв питания не рушит базу.
Внешние ключи включены, поэтому удаление аккаунта само подчищает его сессии и
сохранение. Поля для таблицы лидеров продублированы из сохранения намеренно —
иначе пришлось бы разбирать JSON каждого игрока на каждый запрос; по ним
построен индекс.

При первом запуске поверх старой версии данные из `futbolx.json` переносятся
в базу автоматически, а исходный файл сохраняется рядом с суффиксом
`.migrated`. Повторный перенос не выполняется.

Резервная копия — копированием файла базы вместе с `-wal` и `-shm`, либо:

```bash
sqlite3 data/futbolx.sqlite ".backup 'backup.sqlite'"
```

## Как игра находит сервер

Игра, открытая с самого сервера, определяет его адрес сама: при загрузке она
запрашивает `/api/health` на своём же адресе и принимает ответ, если в нём есть
метка `service: "futbolx"`. Игроку ничего вводить не нужно — на экране входа он
видит только имя и пароль.

Если игра открыта как статический файл (без бэкенда), она работает на локальных
профилях устройства, а адрес сервера можно указать вручную.

## API

Все ответы в JSON. Защищённые методы требуют заголовок
`Authorization: Bearer <токен>`.

| Метод | Путь                  | Описание                                        |
|-------|-----------------------|-------------------------------------------------|
| GET   | `/api/health`         | проверка доступности                            |
| POST  | `/api/auth/register`  | `{name, password}` → `{token, user, save}`      |
| POST  | `/api/auth/login`     | `{name, password}` → `{token, user, save}`      |
| POST  | `/api/auth/logout`    | отзывает текущий токен                          |
| GET   | `/api/me`             | профиль по токену                               |
| GET   | `/api/save`           | сохранение игрока                               |
| PUT   | `/api/save`           | `{save}` — записать сохранение                  |
| DELETE| `/api/account`        | удалить аккаунт вместе с сохранением            |
| GET   | `/api/leaderboard`    | список менеджеров по числу трофеев              |

## Что сделано для безопасности

- Пароли хранятся как `scrypt`-хеш с индивидуальной солью; открытый текст в базу
  не попадает. Сравнение — постоянного времени.
- Клиенту выдаётся случайный токен на 32 байта, в базе лежит только его SHA-256,
  поэтому утечка файла базы не даёт войти под чужой сессией.
- Ограничение частоты: 10 попыток входа за 15 минут на пару «адрес + имя» и
  5 регистраций в час с адреса.
- Ответ на несуществующее имя и на неверный пароль одинаков — перебор имён
  ничего не даёт.
- Тело запроса ограничено 512 КБ, статика не выпускает запрос за пределы папки игры.

Чего здесь нет и о чём стоит знать перед выкладыванием в интернет: HTTPS
(поднимайте за обратным прокси вроде Caddy или nginx), восстановление пароля по
почте и подтверждение адреса. Для домашней сети и небольшой компании друзей
этого набора достаточно, для публичного сервиса — нет.
